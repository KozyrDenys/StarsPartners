# Стандарт баг-репорта QA Assistant

## Цель

Карточка должна позволять продукту быстро оценить влияние, разработчику — воспроизвести проблему, а QA — однозначно проверить исправление. Автоматическая блокировка сценария сама по себе не считается подтверждённым багом.

## Обязательная структура

1. Короткий заголовок в формате `[Компонент][Платформа] симптом` без имени spec-файла.
2. Резюме с одним наблюдаемым фактом, без повторов служебных аннотаций.
3. Триаж: тип, серьёзность, приоритет, компонент, степень подтверждения и воспроизводимость.
4. Пользовательское или бизнес-влияние.
5. Окружение: URL, платформа, viewport, браузер/проект, ОС и время формирования.
6. Данные тестового игрока: почта, пароль, источник и статус проверки входа.
7. Предусловия и минимальные нумерованные шаги.
8. Фактический и ожидаемый результат рядом.
9. Доказательства: скриншот, вложения, сетевой сигнал и полные машинные артефакты.
10. Проверяемые критерии приёмки исправления.
11. Техническая диагностика и команда повтора в конце, а не вместо пользовательского описания.

Баг-репорт содержит пароль тестового игрока в открытом виде по требованиям текущего QA-процесса. Доступ к папке отчётов и создаваемым тикетам должен быть ограничен командой проекта; реальные пользовательские учётные данные использовать запрещено.

## Правила триажа

- `S1`: недоступен бренд, потеря денег/данных, критичный риск безопасности.
- `S2`: заблокирован ключевой пользовательский сценарий, приемлемого обхода нет.
- `S3`: функция ухудшена, проблема локальна или существует обход.
- `S4`: косметическое или малозначительное отклонение.
- Приоритет (`P0–P3`) хранится отдельно от серьёзности: он отражает срочность бизнеса, а не технический ущерб.
- `product-blocked` означает «автотест не смог продолжить из-за состояния продукта» и по умолчанию требует ручного подтверждения.
- `product-warning` — диагностическое отклонение, а не падение теста.
- «Подтверждено» ставится только при прямом артефакте: скриншоте, сетевой записи, проверке DOM/API либо повторном наблюдении.

## Источники практик

- Atlassian Bug Report Template: severity, environment, reproduction steps, expected and actual result.
- Linear Issue Templates: единые свойства и структурированные form templates.
- GitHub Issue Forms: обязательные поля, выпадающие списки, чекбоксы и вложения.
- Atlassian Loom Bug Reporting: короткие шаги, видимое поведение, влияние, окружение и доказательства.
